# Ответы на контрольные вопросы

## 1. Почему bcrypt лучше SHA-256 для паролей?

SHA-256 создан, чтобы считаться быстро: видеокарта перебирает миллиарды вариантов в секунду, поэтому украденные хэши быстро подбираются.

bcrypt специально медленный, и его скорость можно настраивать параметром cost: у нас cost 12, это около 0,25 секунды на одну проверку. Кроме того, bcrypt автоматически добавляет к каждому паролю случайную соль. Одинаковые пароли дают разные хэши, и заранее посчитанные таблицы (rainbow tables) не работают.

## 2. Чем SAST отличается от DAST?

**SAST** анализирует исходный код без запуска приложения («белый ящик»). Он находит проблему ещё на этапе разработки и указывает точную строку. У нас это SpotBugs + Find Security Bugs.

**DAST** атакует уже запущенное приложение снаружи, через HTTP-запросы («чёрный ящик»), например OWASP ZAP. Он видит реальное поведение и ошибки конфигурации, но не показывает, где в коде проблема.

SAST находит проблемы раньше, DAST ближе к реальной атаке. Используют оба подхода.

## 3. Как работает JWT?

JWT — это строка из трёх частей через точку: `header.payload.signature`, каждая часть закодирована в Base64URL.

- **Header** — алгоритм подписи, у нас HS256.
- **Payload** — данные (claims): имя пользователя (`sub`), издатель (`iss`), время выдачи (`iat`) и окончания действия (`exp`). Payload не зашифрован, его может прочитать любой, поэтому секреты туда не кладут.
- **Signature** — HMAC от header и payload, вычисленный на секретном ключе сервера.

При входе сервер выдаёт токен, клиент присылает его в заголовке `Authorization: Bearer`. Сервер заново вычисляет подпись своим ключом и сравнивает её с подписью в токене. Если кто-то изменил payload, подпись не совпадёт. Затем сервер проверяет, что срок `exp` не истёк и издатель правильный. Токены без подписи (`alg=none`) отклоняются.

## 4. Чем опасно не проверять сторонние библиотеки?

Большая часть кода приложения — это чужие библиотеки, и уязвимость в любой из них становится уязвимостью нашего приложения. Пример — Log4Shell в Log4j: удалённое выполнение кода на миллионах серверов.

Риски:
- известные уязвимости (CVE), для которых уже есть готовые эксплойты;
- атаки через цепочку поставок: в пакет внедряют вредоносный код;
- заброшенные библиотеки, которые больше не получают исправлений.

В нашем проекте OWASP Dependency-Check нашёл 9 критических CVE во встроенном Tomcat. Без проверки мы бы о них не узнали. После обновления версии уязвимости исчезли.
